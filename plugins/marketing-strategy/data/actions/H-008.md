## Draft thread

```
1/ If you're running Claude Code across a team of 20+ devs, you're hitting governance problems
   you probably haven't named yet.

   Five things I see every week:

2/ "Our devs all write different prompts."

   There's no shared skill library. Every dev rediscovers the same patterns. The skill that
   one team wrote for code review doesn't make it to the next team. Institutional knowledge
   stays in individual chat logs.

3/ "I can't tell which teams use Claude Code most."

   No usage analytics by department, no cost attribution, no visibility for leadership.
   The CFO asks "is the Claude Code budget justified?" and you don't have data to answer.

4/ "Our security team wants an audit trail of AI tool calls. We don't have one."

   What the agents did, on whose behalf, with what authorisation, and what the result was.
   Current SIEMs have a blind spot for AI activity. Nothing is logged as a real event.

5/ "Plugin and MCP server config drifts per developer."

   Everyone installs what they want locally. When a config changes, everyone updates manually.
   No central registry, no version control, no per-role distribution.

6/ "We need to enforce standards but developers don't read policy docs."

   Governance as documentation doesn't work. It has to be enforced structurally — at the
   tool-call level, before execution, with decisions logged as structured events.

7/ I've been writing about this at systemprompt.io if you want the long version.
   Single Rust binary that sits at the MCP transport layer, runs the governance pipeline,
   emits JSON to your SIEM. You own the binary.

   What are you using to solve any of the five above? Genuinely curious.
```
